# OnePledge layer 1: work packages

Version 1.0, 2026-11-21. Five packages, in order. Each is one implementer run. Each builds on the ones before it and leaves the repository green.

## Rules for every implementer

1. Before anything else read, in full: `docs/BUILD_PLAN.md`, `docs/layer1/CONTEXT.md`, `docs/layer1/SPEC.md`, `docs/layer1/RUBRIC.md`, `contracts/README.md`, and the contract YAML files your package touches.
2. `SPEC.md` is the contract. Do not fill a gap with a guess: if the SPEC is silent or contradicts itself on something that affects correctness, security or a rubric check, stop and report it. Do not edit `SPEC.md`, `RUBRIC.md` or `WORK_PACKAGES.md`.
3. Do not change `contracts/*.yaml` or `contracts/examples/`. If the implementation cannot match the contract, report it. (WP1 may only add the generated files named in its list.)
4. No stubs, no `TODO`, no `NotImplementedError` outside abstract methods, no test-mode branches in product code, no hardcoded expected results, no em dashes. Nothing outside `evaluation/` reads the answer key.
5. Work only inside the folders your package lists. Extend shared files (`Makefile`, root `pyproject.toml`, `README.md`, `.gitignore`) only as your package says.
6. Tests are written with the code. A package is not done until its done-check passes from a clean shell on the build machine, and `make lint`, `make typecheck` and `make test` pass for everything that exists so far.
7. Commit in small, coherent commits with clear messages. Do not commit `.env`, `var/` or generated data (except the files under `contracts/examples/tapes/`).
8. You do not declare the package complete. You hand back: what was built, the done-check output, and any SPEC question. Independent reviewers grade against the rubric IDs listed for the package, and against every earlier package's IDs again.
9. On the build machine: PostgreSQL is at `postgresql://postgres@localhost:55432/postgres`; there is no Docker daemon; install with `pip install --break-system-packages -e`. Use a database prefix of your own for manual runs (`ONEPLEDGE_DB_PREFIX`), and unique names in test fixtures, so parallel work does not collide.

Rubric IDs marked **owns** must pass when the package is handed back. IDs marked **contributes** cannot fully pass yet (they need a later package) but the part this package builds must already satisfy them.

## Order and review

| Order | Package | Review after hand-back |
|---|---|---|
| 1 | WP1 Foundation, doubles, datagen, outside records | Its owned IDs, plus the parts of contributed IDs it built |
| 2 | WP2 Bank agent core A | WP2 owned IDs, and WP1 owned IDs again |
| 3 | WP3 Bank agent core B | WP3 owned IDs, and all earlier owned IDs again |
| 4 | WP4 Bank agent interface | WP4 owned IDs, and all earlier owned IDs again |
| 5 | WP5 Evaluation, demo, stack, docs, sweep | All 70 criteria, from a fresh clone, on one commit |

Until WP5 exists there is no `make up` and no `onepledge-eval`. Reviewers of WP1 to WP4 reach the states a rubric procedure names (STATE-EMPTY, STATE-RUN) by starting the services by hand as the package READMEs describe and by feeding tapes in manifest order through the API or the use cases; where a procedure cannot be run at all yet, the criterion is graded at the WP5 review and the package's own done-check stands in for it.

A package whose review finds failures goes back to an implementer with the concrete failures (criterion, expected, observed, where). It is fixed and reviewed again. The next package starts only when the current one's owned IDs pass. Release is the WP5 review passing all 70.
